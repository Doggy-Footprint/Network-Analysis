## 판정

“수정 시 위험할 수 있는 관련 항목이며, 이 harness에서는 놓칠 조건이 있다”는 조건부 진단을 우선 구현할 수 있다. “실제로 깨질 확률이 높고 에이전트가 이를 놓칠 확률도 높다”는 수치 예측은 이번 문헌 확인만으로 정당화되지 않는다. 위험 후보 생성과 행동 누락 예측을 각각 검증한 뒤 결합해야 한다.

## 1. Target-only 정적 분석이 제공할 수 있는 범위

제안 입력은 저장소 snapshot, 수정 target, 지원 언어·관계 규칙이다. 작업 seed나 정답 발견 시나리오가 필요하지 않다. 전역 분석에서는 분석 가능한 각 위치에 같은 검사를 적용할 수 있다.

| 산출물 | 예시 | 해석 |
|---|---|---|
| 영향 후보 | 호출자, 반환값·타입을 사용하는 위치, 설정 소비자 | 특정 종류의 변경에서 영향을 받을 수 있다는 관계 근거 |
| 이해할 계약 후보 | target이 호출하는 API, 사용 중인 타입·설정의 정의 | target을 바르게 수정하기 위해 확인할 이유가 있는 계약 |
| 검증 수단 | 연결된 테스트, 검증 명령·fixture의 명시적 단서 | 확인 방법을 발견할 수 있는지 평가할 대상 |
| 분석 불확실성 | 동적 dispatch, 반사, 외부 설정, 미지원 framework | 관계를 복원하지 못한 범위. 관계 없음이나 안전함으로 해석하지 않음 |

같은 함수라도 내부 계산 수정, 반환 계약 변경, 삭제는 영향이 다르다. 그러므로 target만 주는 결과는 가능한 변경을 포괄하는 후보이고, 실제 변경 내용 없이 반드시 확인해야 할 전체 집합을 확정하지 않는다. 이는 target-only 입력 제약에서 도출한 설계 한계다.

S1·S2는 후보를 만들고 평가할 연구 기반을 제공한다. 데이터·제어 의존을 더 정밀하게 추출하거나 정적 slicing을 도입할지는 후보 방법으로 남긴다. 이 검토에서 slicing 구현의 비용이나 이 저장소에 대한 효용을 입증하지 않았으므로 도입 결정으로 기록하지 않는다.

기존 ROADMAP의 고정 방향표·형제 구현 전파·깊이 1을 정답으로 승계하지 않는다. 어댑터의 실제 edge 의미와 변경 종류별 반례를 먼저 확인한다. 문서 언급, 이름 일치, 탐색 연결을 일반적인 파손 전파 edge로 혼합하지 않는다.

## 2. AI 에이전트가 고려 범위를 정하는 방식

S3의 관측 가능한 동작은 검색·파일 보기·수정·실행 피드백을 반복하고 문맥을 관리하는 것이다. 해당 실험은 도구가 허용하는 선택지와 결과 표현이 행동에 영향을 준다는 근거다. 내부적으로 “충분히 확인했다”고 판단하는 과정을 정적 그래프로 직접 복원한다는 근거는 아니다. [S3, PRIMARY 88](https://proceedings.neurips.cc/paper_files/paper/2024/hash/5a7c947568c1b1328ccc5230172e1e7c-Abstract-Conference.html)

이 프로젝트에서는 M8에 실제 도구 호출, 반환된 경로·코드 범위, 문맥 보존·축약, 명시적인 계약 확인이나 테스트 실행을 기록하는 방식이 적합하다. 검색어 선택의 이유나 내부 이해 상태는 직접 관측된 사실로 취급하지 않는다. 확인 행동의 판정 기준은 M2~M7에서 실행 전에 정한다.

## 3. 누락 예측에서 구분할 오류

| 상황 | 가능한 판정 | 추가 검증 |
|---|---|---|
| 분석기가 실제 관련 관계를 추출하지 못함 | 분석 커버리지의 누락 | 독립된 계약·변경 사례로 관계 추출 평가 |
| 근거는 있지만 profile의 출력에 나오지 않음 | 해당 조건의 노출 장애 | M8에서 잘림·정렬·읽기 창을 실제 도구와 비교 |
| 노출 가능한데 실행에서 선택하지 않음 | 실행 중 미노출 | 여러 실행에서 빈도와 조건 측정 |
| 해당 코드가 노출됐지만 확인 근거가 없음 | 확인 근거 미관측 | 확인 기준·로그 충분성·작업 결과 검토 |
| 에이전트가 확인을 생략하고 오류를 냄 | 누락과 실패의 동반 관측 | 누락이 원인인지 별도 실험·검토 |

이는 본 프로젝트에 제안하는 측정 분해다. S3·S4가 노출량·문맥 처리의 중요성을 뒷받침하지만 각 상태의 판정 방식과 누락 확률을 제공하지는 않는다.

보정 전에는 위험 후보의 근거와 노출 장애를 별도 열로 보여준다. 예를 들어 “설정 소비 관계가 있으며, 이 profile의 결과 한도에서 해당 근거가 잘린다”는 설명이 가능하다. “수정 실패 확률 80%”처럼 후보 중요도와 임의 접근성 가중치를 결합한 확률은 만들지 않는다.

## 4. M8 통합 검증 순서

다음은 확정된 수치 계약이 아닌 M8 검증 제안이다. M2~M7은 평가 사례, 정적 기대값과 실행 조건을 준비하고, 실제 harness 또는 agent 호출은 하지 않는다.

1. M2~M7에서 지원할 언어·harness, 평가 사례, 확인 행동, 정적 기대값과 표본 계획을 고정한다.
2. M8에서 실제 반환 범위와 확인 행동을 반복 기록한다.
3. Target-only 후보의 precision/recall과 후보 수·검토 부담을 평가하고 참조 그래프와 후보 생성 규칙의 오류를 분리한다.
4. 해당 후보가 실제 실행에서 노출·확인되는지 조사한다. 순위 유효성이 부족하면 누락 순위·확률을 내지 않는다.
5. 구조 또는 harness 하나를 바꾸어 독립 실행으로 비교한다. 작업 성공·필요한 확인을 유지하면서 탐색 부담이 줄어드는지 판정한다.
6. 보정에 쓰지 않은 사례에서 결합 결과를 검증한다. 결합이 유효하지 않아도 근거 기반 후보와 도구의 노출 장애는 각각 보고할 수 있다.

정적 후보의 precision/recall은 독립 평가 집합과 그 한계에 대한 값이다. 변이로 관측한 오류 전파나 통과한 테스트만으로 보편적인 “안전 수정”을 입증하지 않는다. S2는 검증 방법의 보조 근거이며 본 프로젝트의 정확도 목표값을 정해 주지는 않는다.

## 5. 최우선 성공 기준의 반영

M8의 구조 개선 실험은 같은 harness·모델·작업 조건에서 전후 snapshot을 비교한다. Harness 개선 실험은 저장소를 고정한다. 동시에 바꾸면 각각의 단독 효과와 결합 효과를 구분한다.

비용은 실제 노출 토큰·검색/읽기 호출·중복 탐색 등의 원래 축과 준비 비용을 기록한다. 성공한 실행만 남겨 평균을 낮추지 않으며, 실패·중단·확인 누락을 함께 보고한다. 실행 순서와 캐시를 통제하고 반복 실행의 불확실성을 기록한다.

그래프 수치 감소는 가설이다. 실제 작업에서 필요한 확인을 유지하면서 탐색 부담이 감소해야 개선 검증으로 인정한다. S3의 도구 비교와 S5의 context-file 실험은 이런 실측이 필요한 근거지만, 제안하는 구조 개선의 효용을 미리 입증하지는 않는다.
