# Absolute `app.`-rooted imports break router prefix resolution

`FastAPIAnalyzer._resolve_target_router_module` (`framework_analyzers/fastapi/analyzer.py`) matches an `include_router(...)` call's imported router back to the analyzer's own module keys. When project source uses absolute imports rooted at the package name itself (`from app.api.routes.users import router`) while the analyzer is pointed at that same `app/` directory as project root, the analyzer's own module keys never carry the `app.` prefix the import spells out. The match fails, `_resolve_router_hierarchy` never finds a target to attach a prefix to, and every endpoint's `full_path` degrades to its bare decorator path — router-level `prefix=` is silently dropped.

Confirmed against both registered FastAPI fixtures (`fixtures/registry.py`: `fastapi-realworld`, `fastapi-official-template`) while writing `tests/test_analyzer.py::FastAPIRealFixtureSmokeTests` — e.g. `fastapi-realworld`'s `authentication.router` is included with `prefix="/users"` but its `/login` endpoint's `full_path` stays `/login`, not `/users/login`; `fastapi-official-template`'s `users.router` (itself `prefix="/users"`) leaves `read_user_me`'s `full_path` as `/me`, not `/users/me`. Both are absolute-import projects, which appears to be the common real-world pattern (not an edge case) — this likely under-reports router prefixes broadly, not just in these two fixtures.

Fix direction: when resolving an import target against project module keys, also try stripping the importing project's own top-level package name (the root directory's basename) as a prefix before giving up the match.
